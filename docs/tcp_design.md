# KNS TCP Design

## 1. Purpose

This document describes the current TCP architecture implemented in KNS.

KNS models TCP inside an event-driven network simulation. A TCP session is represented locally by a `TCPSession`, which owns the client and server-side `TCPConnection` objects. Network transmission itself is performed through `Packet`, `Link`, `Routing`, and `SimulationEngine`.

This document describes the implementation that currently exists. Reliability mechanisms such as retransmission timers, sliding windows, delayed ACK, fast retransmit, and congestion control are planned extensions and are not yet part of the current TCP architecture.

## 2. Main Components

```text
SimulationEngine
    |
    +-- EventQueue
    |
    +-- TCPSession
    |     |
    |     +-- client TCPConnection
    |     |
    |     +-- server TCPConnection
    |
    +-- Packet
    |
    +-- Routing
    |
    +-- Topology
          |
          +-- Link
```

### 2.1 `SimulationEngine`

`SimulationEngine` is the owner of the simulation clock, event queue, topology, routing tables, TCP sessions, packet statistics, and packets currently in transit.

It is responsible for:

* scheduling events;
* advancing simulation time;
* forwarding packets through links;
* creating TCP sessions;
* starting TCP handshakes;
* generating application-like DATA traffic after establishment;
* scheduling connection close events;
* collecting validation statistics.

Routing tables are currently built when the engine is constructed.

### 2.2 `TCPSession`

A `TCPSession` represents one simulated connection between a source and a destination.

It contains:

* session ID;
* source node;
* destination node;
* session state;
* client-side `TCPConnection`;
* server-side `TCPConnection`;
* traffic-generation state;
* session-level packet counters.

The current implementation models both endpoints inside the same simulation process. The server endpoint is therefore known when the session is created.

### 2.3 `TCPConnection`

`TCPConnection` stores the TCP state and sequence information for one endpoint.

Current state includes:

* TCP state;
* local sequence number;
* expected ACK number;
* local node;
* remote node;
* SYN retry count.

The connection exposes operations for:

* creating SYN;
* creating SYN-ACK;
* creating ACK;
* creating FIN;
* receiving SYN;
* receiving SYN-ACK;
* receiving ACK;
* receiving FIN;
* initiating SYN;
* initiating FIN.

## 4. Connection Establishment

The TCP handshake is implemented through simulation events and packets.

### Step 1 — SYN

`TCPHandshakeEvent` asks the client connection to send a SYN and constructs a `Packet` containing a TCP SYN segment.

The packet is injected into the network through `PacketUtils::sendPacketThroughTopology()`.

### Step 2 — SYN-ACK

When the SYN arrives at the destination, `PacketReceivedEvent` processes it through the server connection.

The server:

1. records the remote sequence number;
2. updates its expected ACK number;
3. enters `SYN_RECEIVED`;
4. constructs a SYN-ACK;
5. sends it through the topology.

### Step 3 — ACK

When the client receives the SYN-ACK, it:

1. validates the ACK against its sequence number;
2. records the peer sequence number;
3. enters `ESTABLISHED`;
4. constructs the final ACK.

When that ACK reaches the server, the server transitions from `SYN_RECEIVED` to `ESTABLISHED`.

Once both endpoints are established, the session transitions to `ESTABLISHED` and the engine generates DATA traffic.

## 5. DATA Transfer

DATA is generated by `PacketGenerationEvent`.

The current implementation uses the client's current sequence number and expected ACK number when constructing a segment.

The payload size is based on the configured packet size.

After creating the segment, the client's sequence number is advanced by the payload size.

```text
PacketGenerationEvent
        |
        v
TCP DATA segment
        |
        v
PacketUtils::sendPacketThroughTopology
        |
        v
SimulationEngine::sendPacket
        |
        v
PacketReceivedEvent
```

When DATA reaches its destination, the receiving endpoint updates its expected ACK number according to the received sequence number and payload size, then generates an ACK.

## 6. Packet Classification

The packet layer derives a high-level `PacketType` from TCP flags.

Current classification includes:

* SYN
* SYN-ACK
* ACK
* DATA
* FIN

A segment containing PSH is treated as DATA after SYN/FIN combinations have been checked.

## 7. Connection Termination

After session traffic is scheduled, `SimulationEngine::generatePackets()` schedules a `TCPConnectionCloseEvent`.

The close event:

1. verifies that the client is still `ESTABLISHED`;
2. calls `send_fin()`;
3. builds a FIN+ACK segment;
4. injects the FIN into the network.

When the peer receives the FIN, it:

1. enters `CLOSE_WAIT`;
2. sends an ACK;
3. sends its own FIN;
4. transitions through the passive-close path.

The active side processes the ACK and peer FIN through its corresponding TCP states.

## 8. Event-Driven Model

TCP behavior is not executed as a blocking procedure. Each protocol action schedules or produces network events.

Important event types currently include:

* `TCPHandshakeEvent`
* `TCPHandshakeTimeoutEvent`
* `PacketGenerationEvent`
* `PacketReceivedEvent`
* `TCPConnectionCloseEvent`

This allows network transmission delay, propagation delay, routing, and protocol processing to coexist in the same simulation timeline.

## 9. Network Interaction

TCP does not directly manipulate links.

The protocol layer creates a `Packet`, then delegates forwarding to:

```text
PacketUtils::sendPacketThroughTopology()
```

The network layer selects the next hop using the engine's routing table.

`SimulationEngine::sendPacket()` then calculates:

```text
transmission time
+
propagation time
```

and schedules the corresponding `PacketReceivedEvent`.

This separation keeps TCP protocol behavior independent from the physical/link model.

## 10. Current Limitations

The current TCP design deliberately remains a simplified transport model.

The following mechanisms are not yet implemented:

* retransmission timeout (RTO);
* retransmission of lost DATA;
* send/receive buffers;
* sliding window;
* receive-window advertisement;
* duplicate ACK tracking;
* fast retransmit;
* delayed ACK;
* congestion control;
* Tahoe/Reno/NewReno/CUBIC;
* a real TCP listener/socket model;
* expiration of TIME_WAIT.

These mechanisms should be implemented incrementally on top of the current architecture rather than being mixed into the existing handshake and packet-routing code.

## 11. Architectural Direction

The intended evolution is:

```text
Current TCP
    |
    +-- sequence numbers
    +-- ACK processing
    +-- FIN handling
    |
    v
Send/Receive Buffers
    |
    v
Sliding Window
    |
    v
RTO + Retransmission
    |
    v
Duplicate ACK Detection
    |
    v
Fast Retransmit
    |
    v
Congestion Control
```

The transport layer should continue to communicate with the network through `Packet` and `SimulationEngine` rather than directly depending on topology internals.
